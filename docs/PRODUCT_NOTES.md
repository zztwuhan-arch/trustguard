# TrustGuard 产品设计笔记

本项目所有政策、门槛和数据均为 prototype；与 rednote 无隶属关系。

目标用户：内容审核人员、Policy PM，以及需要理解或质疑审核决定的发帖人。
核心问题：把可疑内容转换为有依据、可解释、可复核的治理建议，同时控制误伤。

## 关键产品决策

1. 第一版只做 Financial Scam 文本；不用多风险分类掩盖流程深度。
2. 用户内容不能改变政策。模型只提取信号和判断适用性，程序校验引用并控制高影响动作。
3. Singapore 不等于不同风险人群，而是需要处理当地产品语境和待验证权威声明。
4. 删除建议全部人工，优先证明流程可控。代价是高人工负担；以后必须用独立数据分析可自动化的低影响场景。
5. 申诉是新证据入口，不是要求模型维护原答案。通过盲化先前结论降低锚定，但不消除同模型偏差。
6. 用户解释不声称已经执行处罚，人工最终结论须显示审核理由；原型只保存本地状态。

## 衡量与实验

离线：Precision、Recall、FPR、弃判率、灰区升级率、分市场差异。
运营：人工升级率、队列时长、审核一致性、申诉解决率和改判率。
用户：解释理解度调查、补充信息完成率、重复申诉率。以上运营/用户指标除本地改判统计外尚未采集。

下一实验：收集至少 200 条经双人标注/仲裁的多语言独立样本，将规则基线与 OpenAI 输出在相同案例上比较；不在 test set 调阈值。再检验 0.80 门槛与人工容量的关系。

## 职位匹配讲述（基于项目事实）

“我做了一个面向 Global 与 Singapore 的 Financial Scam 治理原型，串起识别、政策 grounding、证据校验、处置建议、用户解释、申诉和人工复核。最重要的设计是把检测与处罚分开：模型并不定义 policy，高影响和不确定案例进入人工审核。我用合成样本评估召回、误伤和人工负担，也暴露了规则基线在隐晦话术与缺失上下文上的局限。”

可以陈述完成的原型能力；不能声称已有真实平台治理经验、线上收益或验证过的大规模模型准确率。
